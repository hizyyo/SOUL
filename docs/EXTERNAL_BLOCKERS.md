# External blockers

This file intentionally lists only requirements that must be satisfied by the product owner or an external party. Engineering work that can be completed inside this repository does not belong here.

| Blocker                                 | Required owner / external action                                                                                                                                 | Closure criteria                                                                                                                                                                                          |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 external validation                  | The product owner recruits the required independent participants, runs the approved day-0/day-7/day-28 validation, and records consented results.                | The validation report contains the required participant count, complete day-7 and day-28 results, adverse-event notes, and a signed owner decision of `GO`, `ITERATE`, or `KILL`.                         |
| Release signing identity                | The owner obtains an organization-controlled Windows code-signing certificate and grants CI access through an approved secret or signing service.                | A clean CI release produces an Authenticode-signed executable whose signature chains to a trusted root, passes timestamp verification, and exposes no private key material to the repository or job logs. |
| Update-channel ownership                | The owner selects and controls the production download/update endpoint and supplies the release-signing public/private key arrangement.                          | The endpoint is under organization control, CI can publish signed update metadata using protected credentials, and a clean-install-to-update rollback exercise is accepted by the owner.                  |
| Browser Companion distribution identity | The owner controls the Chrome/Edge extension publisher accounts and approves the final production extension identity.                                            | Store ownership is verified, the production extension ID is fixed and matches the native-host allowlist, and the submitted ZIP is accepted or explicitly approved for managed/private distribution.       |
| Privacy and legal approval              | The owner or retained counsel approves the production privacy notice, consent language, retention policy, and user-support contact.                              | Approved documents have versioned publication locations and the owner records written release approval for the exact product version.                                                                     |
| Production Gateway providers            | For any P1 hosted Gateway launch, the owner executes provider agreements and supplies organization-owned production accounts, quotas, and billing authorization. | Required provider accounts are active, contractual/data-processing requirements are accepted, spending limits are set, and protected credentials are available to the deployment environment.             |
| macOS and Linux release validation      | The owner provides maintained macOS and Linux CI runners or hardware and platform signing/notarization access where applicable.                              | Clean platform-native builds complete, sidecar/browser integration smoke tests pass, and platform artifacts are signed/notarized according to the approved release policy.                              |
| Upstream desktop dependency advisories  | The owner approves a Tauri/GTK dependency upgrade plan or a documented risk acceptance for transitive GTK3/glib advisories.                                  | `cargo audit` no longer reports actionable unsound/vulnerable dependencies for the shipped platforms, or the signed risk decision names the exact advisories and compensating controls.                  |
