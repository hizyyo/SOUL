# Search and Context Compiler

## Цель

Дать SOUL минимальный разрешённый контекст задачи: детерминированный компилятор, который фильтрует сущности по области, чувствительности, состоянию и времени, упаковывает их в токены (900 по умолчанию, жёсткий максимум 3 000) и не отправляет весь SOUL наружу. Плюс типизированный полнотекстовый поиск по claim/evidence на Rust (FTS5) и предпросмотр пакета в UI.

## Реализовано

### Rust: полнотекстовый поиск (FTS5)

- **`src-tauri/src/db.rs` — `init_fts`**: виртуальная таблица `entity_fts` (FTS5, contentless `content=''`, токенизатор `unicode61 remove_diacritics 2`, колонки `claim`/`evidence` индексируются, `id`/`entity_type`/`status` UNINDEXED). Триггеры `entity_fts_ai/ad/au` на INSERT/DELETE/UPDATE сущностей берут claim/evidence через `json_extract(data, ...)` — индексация прозрачна для любых путей записи (включая импорт пакета, который пишет `entities` напрямую). Бэкафилл: если индекс пуст — INSERT SELECT по всем сущностям.
- **`fts_match_query`**: пользовательский текст → безопасный FTS5 MATCH-запрос. Непрерывные alphanumeric-последовательности (unicode) экранируются кавычками и связываются через AND; `_` и `-` — разделители (`topic_7` → `"topic" AND "7"`); мусорные запросы (спецсимволы, пустота) → `None` → пустой результат, а не ошибка.
- **`search_entities`**: JOIN `entity_fts` ↔ `entities` по rowid, обязательный фильтр `soul_id` (чужие сущности не утекают), ранжирование `bm25` ASC + свежесть DESC, limit зажат в 1..100.
- **`src-tauri/src/lib.rs`**: команда `search_entities_cmd(soul_id, query, limit)` зарегистрирована в invoke_handler.
- **Тесты (8 новых)**: FTS5 скомпилирован в bundled SQLite; поиск по claim/evidence; ранжирование (документ с дублем термина выше, AND-семантика); отсутствие утечек между душами; синхронизация при update/delete; синхронизация при «сыром» INSERT как при импорте; мусорные запросы без ошибок; поиск по 1000 сущностей быстрее 1 с (реально ~мс).

### TypeScript: компилятор контекста

- **`src/data/context.ts` (новый)**: чистая детерминированная функция `compileContext(entities, query) → ContextPack` — без сети, без модели, без часов и случайности. Одинаковое состояние + запрос → байт-в-байт одинаковый пак.
- **Фильтры**: текстовый (релевантность: термин в claim ×2, в evidence ×1; `relevance == 0` отсекается полностью), области (домены/проекты/люди/каналы, пустое = без ограничения), чувствительность (по умолчанию все, кроме `restricted`; `restricted` — только по явному выбору), статусы (по умолчанию только `active`), временное окно `[since, until]`.
- **Приоритеты**: границы (boundary) выше решений, целей, предпочтений и фактов; внутри тира — релевантность → уверенность → свежесть → id (полный детерминированный порядок).
- **Дедупликация superseded**: из сущностей с одинаковым `questionId` остаётся только самая свежая по `updated_at`; ID удалённых попадают в `supersededIds` и видны в паке как `SUPERSEDED: ...`, но в пак не включаются. Legacy-сущности без `questionId` не трогаются.
- **Явные конфликты**: разные ответы на один вопрос (считается до дедупликации) → пары (старое значение → новое) с детерминированным порядком, выводятся в паке секцией `CONFLICTS:`.
- **Упаковка токенов**: консервативная оценка без модели — CJK-символ ≈ 1 токен, остальные ≈ 1/3 (верхняя граница к реальным токенизаторам); стандарт 900, жёсткий максимум 3 000 (clamp); лимит применяется к реальному сериализованному пакету, поэтому превысить бюджет невозможно.
- **Версионирование**: `policyVersion = soul-context-policy/1`; `stateVersion` — 32-битный FNV-1a от упорядоченных `id|updatedAt` включённых сущностей (меняется при любом изменении содержимого).
- **Входной тип `ContextEntity`** — полная форма сущности из Rust (`soul_id`, `created_at`, `updated_at`); из `review.ts` экспортирован `domainForQuestion` (был внутренним).

### UI

- **`src/pages/Context.tsx`**: вместо заглушки — предпросмотр контекста: полнотекстовый поиск (FTS5 через `search_entities_cmd`, дебаунс 250 мс, топ-20 результатов с типом/статусом), фильтры-чипы по доменам/чувствительности/статусам, слайдер бюджета токенов (100–3000) и живой предпросмотр сериализованного пакета с счётчиком «N / M токенов · K сущностей».
- **`src/App.tsx`**: странице Context передаются `soul` и `entities`.

## Как работает

Пользователь открывает вкладку Context: над строкой поиска — чипы областей/чувствительности/статусов и слайдер бюджета; ниже — живой пакет. Поиск ищет по всем сущностям (независимо от фильтров) через FTS5 с ранжированием bm25; фильтры и упаковка применяются только к пакету. Пакет всегда детерминирован: те же сущности и запрос дают тот же текст, версию состояния и счётчик токенов. Чувствительные `restricted` сущности в пак не попадают, пока их уровень не выбран явно; замещённые ответы удаляются, но их ID и конфликты видны в отчёте.

## Проверка безопасности

- **Угрозы**: утечка сущностей между душами при поиске, попадание неразрешённых чувствительных данных в контекст, превышение бюджета токенов (DoS через огромный контекст), недетерминированный/нестабильный контекст, FTS-инъекция через пользовательский запрос, показ чужих данных в предпросмотре.
- **Меры**: `soul_id` обязателен в MATCH-запросе (тест утечек между душами); `restricted` исключён по умолчанию и включается только явным выбором (тесты); жёсткий максимум 3 000 токенов применяется к фактической сериализации (тесты 900/3000/clamp); `stateVersion` детерминирован и меняется при изменении содержимого (тесты); `fts_match_query` экранирует термы и возвращает None для мусора — ошибок/инъекций нет (тесты мусорных запросов); компилятор — чистая функция без сети и случайности.

## Производительность и токены

- Компилятор — чистые O(n) алгоритмы в одном проходе; никаких обращений к БД и LLM на пути пакета.
- FTS-поиск — индексированный bm25 в SQLite, лимит результатов 1..100.
- Оценка токенов детерминированная (CJK ×1, прочее ×1/3), применяется к реальному сериализованному пакету — превысить бюджет невозможно.

## Известные ограничения

- FTS-индексация `claim`/`evidence` идёт из JSON внутри `data`; поля вне JSON (например, будущие метаданные) индексируются только при добавлении в триггеры.
- Строка «tokens: N of M» в паке — оценка, не реальная токенизация LLM; для моделей с иными токенизаторами пак может отличаться на несколько процентов, жёсткий максимум при этом всё равно соблюдается.
- Чипы статусов не предлагают «candidate» по умолчанию — пак по умолчанию собирает только `active`; пересборка из кандидатов возможна включением статуса вручную.
- Конфликты подсвечивают только различия значений ответов на один вопрос; противоречия между разными вопросами — задача SESSION-08+.

## Повторная проверка и исправленные баги (review-pass)

По результатам аудита сессии (полный прогон проверок + ручной код-ревью по правилам universal/typescript/rust) исправлено:

- **Баг (бюджет): накладные расходы пакета не учитывались при упаковке.** Пробная оценка считала только тело сущностей, а финальный пак содержит заголовок (policy/state/tokens/entities) и секции `CONFLICTS:`/`SUPERSEDED:` — при бюджете 3 000 пак мог выйти за жёсткий максимум на ~40–200 токенов. Теперь пробная оценка включает полный пак, а финальная сборка гарантирует `tokenEstimate ≤ maxTokens` по построению (страховочный сброс самого низкоприоритетного элемента). Тест `counts header, conflicts and superseded report toward the budget`.
- **Гонка (UI): устаревший FTS-запрос перезаписывал результаты.** При смене/очистке поиска in-flight ответ от предыдущего запроса мог вернуть старые хиты в пустое поле поиска; флаг «…» сбрасывался преждевременно. Добавлен счётчик поколений запроса (seq-гард в `.then`/`.catch`/`.finally`).
- **Детерминизм: порядок `conflicts` и `supersededIds` зависел от порядка входного массива** (а `list_entities` сортирует только по `created_at DESC` — при одинаковых датах порядок не гарантирован). Оба списка теперь сортируются по id — пак одинаков при любом порядке входа (тест `same state in any input order`).
- **NaN-бюджет**: `maxTokens: NaN` раньше давал пустой пак и надпись «NaN»; теперь — дефолт 900 (тест).
- **Утечка сырого JSON**: при отсутствии `claim` в data fallback подставлял весь необработанный JSON в пак; теперь — пустая строка.
- **UX-подсказки**: пустые чипы чувствительности/статусов показывают «default: all except restricted» / «default: active only» (пусто = дефолт, а не «ничего не выбрано»).

Проверки после фиксов: `cargo test` 63/63, clippy чисто, `pnpm test` 101/101 (+3: бюджет с накладными расходами, детерминизм при обратном порядке, NaN-бюджет), typecheck/lint/prettier/build — PASS.
