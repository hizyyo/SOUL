# SOUL ULTRA-MVP

## Контекст реализации, матрица функций, тарифы и мастер-промпт для модели-разработчика

**Версия:** 1.0  
**Дата:** 29 июля 2026 г.  
**Использовать вместе с:** `SOUL_MASTER_PLAN.md`  
**Назначение:** передавайте этот документ мощной ИИ-модели, которая пишет код, а затем по одному отправляйте промпты отдельных сессий.

---

## 0. Краткое описание для основателя

SOUL — не чат-бот, не «второй мозг», не универсальный API памяти и не промпт личности.

SOUL — локальная среда выполнения для принадлежащих пользователю:

- решений;
- предпочтений;
- границ;
- целей;
- стиля общения;
- происхождения данных;
- переносимости между моделями;
- полномочий агентов.

Пользователь создаёт `ilya.soul` через быструю интерактивную калибровку, подключает его к уже используемым AI-инструментам и продолжает работать прямо в Codex, Claude Code, Cursor, ChatGPT, Claude или другом клиенте. SOUL не предоставляет собственного окна общения.

В дальнейшем продукт становится уровнем полномочий для ИИ-агентов, но только через обязательный **SOUL Gateway**. Добровольный callback агента не является защитой. Если агент по-прежнему владеет учётными данными целевого сервиса, он может обойти уровень политик.

Ultra-MVP должен восприниматься как серьёзный новый продукт, но оставаться достаточно небольшим, чтобы один быстрый основатель и одна сильная ИИ-модель могли выпустить его без архитектуры, которую невозможно протестировать.

```text
Калибровка
→ Подключение существующего AI-клиента
→ Работа в этом клиенте
→ Улучшение SOUL
→ Управление одним безопасным действием
```

Главная демонстрация:

```text
5-минутная калибровка
→ локальный .soul
→ подключение Codex или другого существующего клиента
→ запрос пишется в исходном клиенте
→ клиент получает минимальный контекст от SOUL
→ тот же SOUL подключается к другому клиенту
→ локальная блокировка демонстрационного действия на $600 за миллисекунды
```

Главное утверждение:

> **Интеллект изменился. Человек — нет.**

Нельзя утверждать, что ultra-MVP полностью предсказывает человека или повсеместно управляет любым агентом. Сейчас он измеряет сходство предпочтений, а позднее будет поддерживать прогнозирование будущих решений. Действия принудительно контролируются только тогда, когда путь выполнения проходит через SOUL Gateway.

## 1. Неизменяемые продуктовые решения

Эти решения зафиксированы. Модель-разработчик не должна вольно их переосмысливать.

1. Источник истины находится локально.
2. На любом тарифе пользователь может экспортировать и удалить данные.
3. Полезный SOUL создаётся без внешнего импорта. Экспорт ChatGPT — первый необязательный источник в разделе `Улучшить SOUL`.
4. SOUL не имеет собственного общего окна чата и не конкурирует с AI-клиентами пользователя.
5. P0 подключается к существующим клиентам через узкие адаптеры: MCP для поддерживаемых coding-клиентов и SOUL Browser Companion для обычных веб-чатов ChatGPT, Gemini и Claude.
6. Первое содержательное сравнение проводится с вручную проверенным базовым профилем `B1`, а не с пустым промптом.
7. В слепых тестах порядок ответов всегда случаен.
8. В слепых тестах всегда есть вариант `Ни один`.
9. До фиксации выбора слепой тест не раскрывает, какой ответ использовал SOUL.
10. Результат слепого теста предпочтений не представляется доказательством предсказания будущих решений.
11. Политики декларативны и детерминированы на быстром пути.
12. Тяжёлое рассуждение используется только как резервный путь.
13. Проверка политики не является принудительным контролем, если действие не выполняется через SOUL Gateway.
14. В управляемом режиме агент не получает прямые учётные данные целевого сервиса.
15. У каждого важного вывода есть сведения о происхождении.
16. Чувствительные предполагаемые воспоминания требуют подтверждения.
17. Стандартный контекст — 400–900 токенов; жёсткий максимум — 3 000 токенов.
18. Цель p95 локальной политики — менее 5 мс.
19. Цель p95 локального пути контекста — менее 75 мс.
20. По умолчанию исходный персональный промпт не журналируется на сервере.
21. Нет пожизненного тарифа синхронизации.
22. Нет безлимитного тарифа тяжёлого рассуждения.
23. В ultra-MVP нет маркетплейса.
24. Графовый интерфейс не является основным.
25. Нет скрытого наблюдения за рабочим столом, браузером, почтой или микрофоном.
26. Каждая завершённая сессия заканчивается тестами, проверкой безопасности, журналом сессии и Git-коммитом.

## 2. Определение ultra-MVP

### 2.1 Минимальный законченный продукт

Ultra-MVP содержит следующие видимые пользователю возможности:

1. Создание локального SOUL.
2. Пятиминутная интерактивная калибровка без внешнего импорта.
3. Проверка и исправление сущностей SOUL.
4. Сборка минимального контекста.
5. Подключение существующих AI-клиентов без переноса работы в SOUL.
6. Автоматическая контекстная интеграция с ChatGPT Web, Gemini Web и Claude Web через Browser Companion.
7. Слепой A/B-тест персонализации.
8. Демонстрация одной локальной детерминированной блокировки политикой и одного имитированного действия Gateway.

| Происхождение | Да | Предотвращает выдуманную идентичность и позволяет исправлять данные |
| Входящие кандидаты | Да | Пользователь управляет активацией |

| Флаги функций | Да | Безопасный выпуск и управление тарифами |
| Журналы сессий | Да | Рабочая дисциплина и доверие инвесторов |

| Регрессионные тесты безопасности | Да | Проверяют инъекции промптов, доступ и обход политик |

### 2.3 Функции P1 после прототипа для привлечения инвестиций

- Prospective Decision Test (тест будущих решений) с зафиксированными прогнозами.
- Настоящий коннектор SOUL Gateway с изоляцией учётных данных.
- Remote MCP и нативные app-коннекторы для размещённых AI-клиентов.
- Зашифрованная синхронизация.
- Импорт экспортов ChatGPT и Claude как необязательных источников улучшения.
- Локальная модель эмбеддингов.
- Гибридный лексический и семантический поиск.
- Биллинг Stripe.
- Публичные обезличенные карточки оценки.
- Сопряжение устройств и восстановление ключей.
- Один обратимый коннектор, например имитация системы задач.

### 2.4 Функции P2

- Несколько веток SOUL.
- Адаптеры почты и календаря.
- SDK агента.
- Командные политики.
- Корпоративные SSO и SCIM.
- Развёртывание в VPC.
- Маркетплейс коннекторов.
- Совокупные сравнительные тесты с сохранением приватности.
- Экосистема пакетов политик.

### 2.5 Явно исключённые цели

Не реализовывать в ultra-MVP:

- собственную фундаментальную модель;
- непрерывное автономное обучение;
- выполнение произвольного кода внутри `.soul`;
- полноценную систему CRDT;
- автоматизацию браузера;
- импорт истории ChatGPT или Claude;
- наблюдение за рабочим столом;
- незашифрованную облачную память;
- векторную базу данных;
- социальную сеть;
- мобильное приложение;
- семейный режим;
- корпоративную панель администратора;
- автономную отправку почты;
- финансовые действия;
- разрушительные действия;
- производственные заявления об имитированном Gateway.

### 2.6 Фазы сессий

```text
SESSION-00..SESSION-14
Fundraising prototype P0: реализовать, проверить на внешних пользователях и только после этого продолжать.

SESSION-15..SESSION-18
Расширение P1 и запуск: выполнять только если P0 прошёл kill criteria, есть подтверждённый спрос и основатель явно решил продолжать.
```

SESSION-15 с биллингом не входит в исходный ultra-MVP. Нельзя строить Stripe, платные права и production-запуск до проверки Blind Preference Test, удержания и готовности пользователей платить.

## 3. Пользовательский опыт продукта

### 3.1 Навигация

Используйте только пять основных разделов:

```text
Главная
Входящие
Тесты
Контекст
Настройки
```

Не создавайте интерфейс, построенный прежде всего вокруг графа. Пользователь всегда должен понимать следующий шаг.

### 3.2 Главная

Показывать:

- состояние SOUL;
- число подтверждённых сущностей;
- ожидающих кандидатов;
- подключённые AI-клиенты;
- результат последнего теста;
- последнее событие политики;
- один главный призыв к действию.

Состояния главного призыва:

```text
Создать SOUL
Начать калибровку
Продолжить калибровку
Активировать SOUL
Подключить AI-инструмент
Проверить переданный контекст
Улучшить SOUL
```

В приложении SOUL нет общего поля запроса и ленты ответов. Главный экран управляет локальным runtime, подключениями, прозрачностью, подтверждениями и разрешениями. Пользователь пишет рабочий запрос только в исходном AI-клиенте.

### 3.3 Входящие

Для каждого кандидата показывать:

- типизированную категорию;
- утверждение простым языком;
- уверенность;
- дату источника;
- фрагмент источника с маскировкой чувствительного текста при необходимости;
- причину предложения;
- область действия;
- действия: Подтвердить, Изменить, Отклонить.

Никогда не показывайте необъяснённый созданный ИИ ярлык личности как истину.

### 3.4 Предпросмотр контекста

До передачи контекста поставщику показывать:

```text
Задача
Поставщик
ID сущностей
Типы сущностей
Классы чувствительности
Оценка токенов
Срок действия
```

Пользователь может разрешить один раз, разрешить для проекта или запретить.

### 3.5 Слепой тест

Порядок теста:

1. Показать вопрос.
2. Создать A и B с одинаковыми настройками поставщика.
3. Случайно определить порядок показа.
4. Уравнять видимые метаданные ответов.
5. Предложить выбрать A, B или «Ни один».
6. Сохранить выбор до раскрытия варианта.
7. Показывать сводные результаты только после достаточного числа раундов.

Экран теста не должен раскрывать токены, задержку, ID ответов или метки вариантов.

### 3.6 Ошибки в интерфейсе

Каждая ошибка должна отвечать:

```text
Что произошло?
Какие данные затронуты?
Можно ли повторить попытку?
Какое следующее действие безопасно?
```

Не показывайте исходные трассировки стека в обычном интерфейсе. Журналируйте их локально с ID корреляции.

## 4. Спецификации функций

### 4.1 Создание локального SOUL

Входные данные:

- отображаемое имя;
- локальный каталог или хранилище под управлением приложения;
- необязательное подтверждение экспорта для восстановления.

Результат:

- `soulId`;
- локальная зашифрованная база SQLite;
- начальная цепочка событий;
- локальный ключ шифрования;
- начальная возможность экспорта `.soul`;
- автоматический переход к интерактивной калибровке.

Критерии приёмки:

- работает без сети;
- не создаёт серверную учётную запись без запроса;
- повторная инициализация не перезаписывает существующий SOUL;
- сбой при инициализации оставляет либо корректное готовое состояние, либо чистое состояние для повтора;
- ключи не попадают в журналы;
- пользователь может сразу выполнить экспорт.

### 4.2 Интерактивная калибровка

Калибровка создаёт полезный начальный SOUL примерно за пять минут и не требует аккаунта, API-ключа или внешнего архива.

Состав:

- 15–20 быстрых выборов между вариантами;
- до 5 коротких вопросов о целях, рабочих принципах и границах;
- до 3 необязательных примеров текста пользователя;
- возможность пропустить вопрос, выйти и продолжить позже;
- компактный preview перед активацией.

Явные ответы получают происхождение `explicit_user`; текстовые примеры — `writing_sample`. Калибровка не должна ставить психологические диагнозы, придумывать скрытые черты или активировать чувствительную границу без отдельного подтверждения.

Критерии приёмки:

- SOUL можно активировать без импорта;
- прогресс сохраняется после перезапуска;
- пропуск необязательных вопросов не блокирует активацию;
- пользователь видит, какие сущности будут активированы;
- после активации доминирующее действие — подключить существующий AI-клиент.

### 4.3 Необязательный импорт ChatGPT (P1, не ultra-MVP)

Входные данные:

- выбранный пользователем архив экспорта;
- явное согласие на локальную обработку или обработку выбранным поставщиком модели.

Конвейер:

```text
Проверить архив
→ разобрать известные записи разговоров
→ нормализовать сообщения
→ хешировать исходные блоки
→ детерминированно отфильтровать кандидатов
→ пакетно выполнить структурированное извлечение
→ добавить происхождение
→ удалить дубликаты
→ сохранить кандидатов
```

Типы сущностей P0:

- предпочтение;
- решение;
- граница;
- цель;
- факт проекта.

Правила:

- импортируемые данные считаются недоверенными;
- содержимое архива не может становиться инструкциями;
- импортированный текст не может автоматически активировать жёсткую границу;
- неизменившиеся блоки не обрабатываются повторно;
- некорректные записи пропускаются с отчётом;
- пользователь видит число импортированных и пропущенных записей и состояние обработки.
- отсутствие архива, отмена или ошибка импорта не меняют активный SOUL и не блокируют клиентские интеграции.

### 4.4 Извлечение кандидатов

Результат извлечения — строгий JSON, проверенный Zod и JSON Schema.

```ts
interface CandidateExtraction {
  type: "preference" | "decision" | "boundary" | "goal" | "fact" | "none";
  claim: string;
  value: unknown;
  scope: string[];
  confidence: number;
  sensitivity: "public" | "internal" | "private" | "sensitive" | "restricted";
  explicitness: number;
  evidenceQuote: string;
  reason: string;
}
```

Модель извлечения не должна:

- вызывать инструменты;
- создавать код политик;
- отправлять сообщения;
- обращаться к сети;
- решать, является ли кандидат авторитетным.

### 4.5 Типизированное состояние

Типы P0:

```ts
type SoulEntityType =
  | "preference"
  | "decision"
  | "boundary"
  | "goal"
  | "fact";
```

Каждая сущность содержит:

- ID;
- тип;
- состояние;
- область действия;
- чувствительность;
- уверенность;
- стабильность;
- ID доказательств;
- временные метки источников;
- временные метки создания и обновления;
- ссылки замещения и конфликтов.

### 4.6 Входящие кандидаты

Поведение активации:

| Кандидат | По умолчанию |
|---|---|
| Явное предпочтение с низким риском | Предложение, которое можно подтвердить |
| Явная граница пользователя | Активна после явного подтверждения |
| Предполагаемая граница | Никогда не активна без подтверждения |
| Чувствительный вывод | Требуется подтверждение |
| Факт проекта | Кандидат или активный, если импортирован явно |
| Противоречивое утверждение | Оспаривается |

### 4.7 Компилятор контекста

Входные данные:

```ts
interface ContextRequest {
  task: string;
  projectId?: string;
  purpose: string;
  recipient: string;
  maxSensitivity: string;
  tokenBudget: number;
}
```

Результат:

```ts
interface CompiledContext {
  text: string;
  entityIds: string[];
  policyVersion: string;
  stateVersion: string;
  estimatedTokens: number;
  redactions: string[];
  expiresAt: string;
}
```

Порядок сборки:

1. жёсткие границы;
2. применимые политики;
3. относящиеся к задаче решения;
4. относящиеся к задаче предпочтения;
5. факты нужной области;
6. конфликты и неопределённость;
7. ID происхождения.

По умолчанию никогда не отправляйте всю локальную базу или исходную историю.

Основной потребитель компилятора — внешний AI-клиент, подключённый к локальному runtime. SOUL возвращает контекст через MCP или Browser Companion, но не создаёт собственного общего чат-интерфейса.

### 4.8 Клиентские интеграции

Используйте один интерфейс клиентского адаптера:

```ts
interface SoulClientAdapter {
  id: string;
  detect(): Promise<ClientDetection>;
  connect(config: SoulConnectionConfig): Promise<ConnectionReceipt>;
  disconnect(): Promise<void>;
  capabilities(): ClientCapabilities;
}
```

Пути P0:

- локальный MCP-сервер для поддерживаемых coding-клиентов;
- Browser Companion для ChatGPT Web, Gemini Web и Claude Web в Chromium-браузерах.

Интеграции должны:

- не создавать собственного окна чата;
- устанавливать конфигурацию только после явного клика пользователя;
- создавать backup изменяемой конфигурации и поддерживать rollback;
- показывать состояние подключения и последний disclosure receipt;
- возвращать только скомпилированный разрешённый контекст;
- не читать историю внешнего клиента без отдельного разрешения и поддерживаемого API;
- не выполнять отправку сообщения без явного действия пользователя.

Browser Companion работает так:

```text
Пользователь открывает обычный ChatGPT/Gemini/Claude Web
→ расширение показывает SOUL ON рядом с полем ввода
→ пользователь пишет запрос как обычно
→ перед отправкой расширение передаёт текущую задачу локальному runtime через Native Messaging
→ runtime собирает разрешённый контекст
→ расширение добавляет структурированный SOUL context к исходящему сообщению
→ ответ остаётся в обычном веб-чате
→ локально создаётся disclosure receipt
```

Ограничения безопасности Browser Companion:

- разрешения только для явно поддерживаемых доменов;
- соединение только с зарегистрированным Native Messaging host SOUL;
- проверка extension ID, версии протокола, nonce и размера сообщения;
- контекст не хранится в extension storage;
- расширение не читает другие вкладки, cookies, пароли или полную историю чатов;
- пользователь видит индикатор, число передаваемых сущностей и может отключить SOUL для одного сообщения;
- site adapters версионируются, имеют health check и fail closed при неизвестной разметке;
- расширение не нажимает Send самостоятельно и не выполняет действия от имени пользователя.

### 4.9 Базовый профиль B1

Пользователь создаёт или проверяет короткий профиль из подтверждённых результатов калибровки. Необязательные импортированные сведения могут улучшить следующую версию B1 после отдельного подтверждения.

Базовая версия:

```text
та же модель
+ тот же вопрос пользователя
+ тот же бюджет токенов
+ те же ограничения результата
+ короткий профиль, проверенный вручную
- компилятор контекста SOUL
- история решений SOUL
```

Это сильнейшая дешёвая базовая версия. Полный SOUL должен её превзойти, иначе продукт следует упростить.

### 4.10 Blind Preference Test

P0 поддерживает:

- 20 раундов;
- случайную позицию A/B;
- `Ни один`;
- одного поставщика и одну модель;
- фиксированную температуру или детерминированные настройки, где доступны;
- равные бюджеты токенов;
- скрытое сопоставление вариантов;
- расчёт результата;
- доверительный интервал Уилсона;
- точный биномиальный p-value по результатам без ничьих;
- ID и версию модели;
- определение и версию baseline B1;
- признак held-out для каждого вопроса;
- метод создания набора вопросов;
- суммарные input/output tokens и оценку стоимости;
- экспортируемую обезличенную карточку результата.

Формулировка P0:

```text
Сходство предпочтений
```

Запрещённая формулировка:

```text
Ваш клон предсказал вас
```

### 4.10 DSL политик

P0 поддерживает только безопасные типизированные условия:

- сравнение сумм;
- сопоставление доменов;
- вид действия;
- сопоставление получателя;
- чувствительность данных;
- обратимость или необратимость действия;
- явное подтверждение пользователя;
- окружение.

Эффекты:

```text
allow
deny
require_confirmation
redact
```

Нет динамического `eval`. Нет произвольных регулярных выражений без тайм-аута. Нет сетевых вызовов со стороны политики.

### 4.11 Имитированный Gateway

Gateway P0 — локальная имитация с поддельным коннектором.

Она демонстрирует:

```text
Агент предлагает покупку на $600
→ действие нормализуется
→ политика блокирует его
→ коннектор не выполняется
→ создаётся подписанная локальная квитанция
```

Метка в интерфейсе:

```text
Имитация: внешнее действие не выполнялось.
```

Настоящая изоляция учётных данных и атомарное выполнение относятся к P1. Никогда не представляйте имитацию P0 как защиту производственного уровня.

### 4.12 Экспорт и удаление

P0:

- экспорт `.soul`;
- экспорт человекочитаемого JSON;
- экспорт сводки Markdown;
- безопасный обратный импорт собственного `.soul`;
- удаление выбранных сущностей;
- удаление всех локальных данных;
- очистка ключей после подтверждения;
- отображение квитанции об удалении.

Пакет `.soul` в P0 обязан:

- использовать проверенные криптографические библиотеки, а не самописное шифрование;
- шифровать содержимое экспортного пакета;
- использовать подпись локального доверенного устройства;
- включать hash содержимого и версию схемы;
- запрещать исполняемый код;
- иметь ограничения размера и глубины;
- проверять подпись, hash и схему до импорта;
- импортироваться сначала во временное sandbox-хранилище;
- показывать пользователю preview до применения;
- безопасно отклонять неподписанный, повреждённый или неизвестный пакет.

В P0 облачная синхронизация должна быть явно помечена как недоступная. Не подразумевайте очистку сервера, если серверных данных нет.

## 5. Как SOUL побеждает конкурентов

### 5.1 Принцип конкуренции

Не побеждайте количеством обычных функций. Сделайте одно утверждение измеримым, а одну границу безопасности — настоящей.

Сильнейшая атака на конкурента — воспроизводимые доказательства, а не оскорбления или слайды с количеством функций.

- происхождение доказательств;
- принудительное применение политик;
- минимизация контекста;
- prospective-оценка;
- непрерывность между моделями.

Если она достаточна, выпустите профиль из десяти строк и удалите лишнюю инфраструктуру.

## 7. Рекомендуемый технический стек

### 7.1 Выбор стека

Используйте гибридный стек, но отделяйте ядро предметной области от интерфейса и облака:

```text
Оболочка desktop: Tauri 2
Среда безопасности/хранения: Rust
Интерфейс desktop: React + TypeScript + Vite + Tailwind
Локальная база: SQLite + FTS5
Проверка: Zod на границах TypeScript + JSON Schema для пакетов
Web/маркетинг: текущая исправленная Next.js Active LTS + App Router + Tailwind
Аутентификация/облачные метаданные: Supabase Auth + Postgres + RLS
Зашифрованная синхронизация: Supabase Postgres/Storage, только P1
Пограничный API: Cloudflare Workers + Hono
Брокер управляемых моделей: Cloudflare Worker или прямые адаптеры поставщиков
Платежи: Stripe, биллинг P1
Тестирование: Vitest + Playwright + тесты Rust + property/fuzz-тесты
Наблюдаемость: структурированные локальные события в стиле OpenTelemetry, удалённые сводки по согласию
```

### 7.2 Почему этот стек

- Tauri даёт небольшую desktop-оболочку, а Rust защищает привилегированные операции.
- SQLite быстр, переносим и естественно поддерживает локальный подход.
- Rust подходит для криптографии, файлового доступа, оценки политик и границ IPC.
- TypeScript подходит для интерфейса, адаптеров, схем и быстрой продуктовой разработки.
- Supabase сокращает работу над аутентификацией и метаданными, но незашифрованный SOUL хранить там нельзя.
- Cloudflare Workers и Hono подходят для небольших API без состояния, webhook биллинга, маршрутизации поставщиков и ограничения частоты.
- Next.js предназначен для маркетинга, потоков учётных записей/устройств и публичных обезличенных результатов, а не для привилегированных операций с локальной памятью.
- Для нового проекта используйте текущую исправленную Active LTS, а не Next.js 14. На 29 июля 2026 г. официальный выпуск безопасности называет Next.js 16.2.11 Active LTS, а 15.5.21 — Maintenance LTS. Зафиксируйте выбранную ветку и быстро устанавливайте исправления безопасности.
- При интеграции в существующее приложение Next.js 14 выделите отдельную сессию миграции до добавления аутентифицированных production-маршрутов. Не смешивайте незаметно обновление фреймворка с несвязанной сессией функции.

Перед реализацией проверьте официальную документацию:

- Tauri: `https://v2.tauri.app/`
- Supabase Auth и RLS: `https://supabase.com/docs/guides/auth` и `https://supabase.com/docs/guides/database/postgres/row-level-security`
- Аутентификация Supabase Edge Functions: `https://supabase.com/docs/guides/functions/auth`
- Выпуски безопасности Next.js: `https://nextjs.org/blog`
- Cloudflare Workers: `https://developers.cloudflare.com/workers/`
- Cloudflare AI Gateway: `https://developers.cloudflare.com/ai-gateway/`
- Спецификация MCP: `https://modelcontextprotocol.io/specification/`

### 7.3 Структура репозитория

Для пустого репозитория:

## 8. Правила данных и безопасности

### 8.1 Классификация данных

```text
public
internal
private
sensitive
restricted
```

### 8.2 Секреты

Никогда не хранить в:

- Git;
- журналах сессий;
- снимках экрана;
- аналитике;
- сообщениях об ошибках;
- публичных тестовых данных;
- экспорте `.soul` по умолчанию;
- исходных сборках frontend.

Для локальной разработки используйте переменные окружения, для развёрнутых сервисов — менеджеры секретов.

### 8.3 Web-аутентификация и кеширование

- Используйте Supabase Auth с проверяемыми сервером сессиями и RLS.
- Не доверяйте ID пользователя, переданному клиентом.
- Не кешируйте ответы обновления аутентификации, callback-ответы и ответы, устанавливающие cookie.
- Не помещайте аутентифицированные HTML- или API-ответы в общие кеши.
- Помечайте чувствительные к аутентификации маршруты как динамические или `no-store` в соответствии с выбранной версией фреймворка.
- Проверяйте цели перенаправления по списку разрешённых.
- Обновляйте сессии после чувствительных изменений учётной записи.
- Тестом двух одновременных пользователей докажите, что данные сессий не пересекают границы кеша.

### 8.4 Локальный IPC

Интерфейс desktop не должен получать произвольный доступ к базе.

Используйте узкие команды:

```text

import_archive
list_candidates
review_candidate
compile_context
run_blind_test_round
evaluate_policy
export_soul
delete_soul
```

Проверяйте каждую команду на границе Rust. Одной проверки TypeScript недостаточно.

### 8.5 Импортированное содержимое

Считайте каждое импортированное сообщение недоверенными данными.

Обязательные меры:

- системный промпт только для извлечения;
- отсутствие инструментов при извлечении;
- строгая схема результата;
- максимальный размер источника;
- максимальный размер цитаты;
- метка загрязнения;
- запрет прямого преобразования импортированного текста в политику;
- враждебные тестовые данные инъекций промпта;
- подтверждение пользователя для сущностей, несущих полномочия.

### 8.6 Безопасность Gateway

P0 только имитирует коннектор.

Требования настоящего Gateway P1:

- агент не владеет учётными данными назначения;
- Gateway владеет учётными данными коннектора или выступает их брокером;
- у действия уникальный ID;
- hash полезной нагрузки привязан;
- есть nonce и срок действия;
- capability одноразовая;
- привязаны коннектор и окружение;
- выполнение по возможности идемпотентно;
- проверка после действия зависит от коннектора;
- неподдерживаемая проверка возвращает `authorized_but_unverified`;
- каждое действие создаёт аудиторскую квитанцию.

### 8.7 Категории тестов безопасности

Каждая относящаяся к ним сессия должна проверять:

- обход путей;
- вредоносный архив;
- слишком большой ввод;
- некорректный JSON;
- SQL-инъекцию;
- XSS во фрагментах доказательств;
- инъекцию промпта;
- повышение полномочий кандидата;
- обход политики;
- повтор capability действия;
- неверную привязку учётной записи;
- истёкшую capability;
- дублирующее действие;
- утечку секретов в журналы;
- неразрешённый локальный IPC;
- сломанные политики RLS;
- понижение или устаревший флаг функции;
- экспорт данных другого SOUL.

## 10. Стратегия тестирования

### 10.1 Пирамида тестов

```text
Много модульных тестов
```

- обнаружение конфликтов;

- оценку AST политики;
- истечение capability;
- проверки функции по тарифу;
- статистические расчёты.

### 10.3 Интеграционные тесты

Проверять:

- миграции SQLite;
- перестроение проекции событий;
- импорт ChatGPT;
- проверку кандидатов;
- имитации адаптеров поставщиков;
- создание базовой версии B1;
- сохранение слепого теста;
- экспорт и удаление;
- локальный IPC.

### 10.4 Сквозные тесты

Минимальные сценарии:

1. Создать SOUL офлайн.
2. Импортировать тестовый архив.
3. Одобрить и отклонить кандидатов.
4. Собрать контекст с маскировкой.
5. Провести 3 слепых раунда.
6. Заблокировать имитированную покупку.
7. Экспортировать и удалить все данные.
8. Перезапустить приложение и проверить состояние.

### 10.5 Набор регрессионных тестов безопасности

Поддерживать тестовые данные для:

- архива с инъекцией промпта;
- вредоносного HTML в доказательстве;
- огромного архива;
- дублирующего события;
- устаревшей политики;
- повторно использованной capability;
- ID другого пользователя;
- повреждённой базы;
- неверной подписи;
- неподписанного импорта;
- неизвестной версии схемы;
- содержимого, похожего на секрет;
- вредоносной ошибки поставщика.

### 10.6 Ворота качества

Не сливать функцию, если:

- тесты не проходят;
- проверка типов не проходит;
- lint не проходит;
- тесты безопасности не проходят;
- функция меняет контракт без миграции;
- исходные приватные данные появляются в журналах;
- критерии приёмки не продемонстрированы;
- отсутствует журнал сессии;
- отсутствует коммит.

## 13. Правила проведения сессий

### 13.1 Одна сессия — одна функция

В каждой сессии должны быть:

- один результат;
- один список приёмки;
- один журнал сессии;
- один целевой коммит.

Если обнаруженная проблема находится вне области сессии:

1. Исправьте её только тогда, когда она блокирует безопасность, корректность или тесты.
2. Иначе запишите её в очередь следующей сессии.
3. Не расширяйте функцию скрытно.

### 13.2 Расположение журнала сессии

```text
docs/session-log/SESSION-XX.md
```

### 13.3 Протокол коммита

Перед коммитом:

```text
git status --short
git diff --check
git diff --stat
```

Запустите относящиеся проверки, затем:

```text
git add <only-intended-files>
git commit -m "feat(soul): <short feature> [session-XX]"
```

Никогда:

- не используйте `git reset --hard`;
- не используйте `git checkout --` для удаления работы;
- не изменяйте коммит через amend без явного запроса;
- не добавляйте в stage несвязанные файлы;
- не коммитьте секреты или личные данные;
- не создавайте поддельный пустой коммит.

### 13.4 Обязательный отчёт сессии

```markdown
# Сессия XX: <функция>

## Цель

## Реализовано

## Изменённые файлы

## Изменённые контракты или миграции

## Запущенные тесты

## Проверка безопасности

## Влияние на производительность и токены

## Известные ограничения

## Последующие сессии

## Коммит
```

### 13.5 Определение готовности

Сессия считается завершённой только когда:

- реализация существует и соответствует приёмке;
- тесты добавлены или обновлены;
- относящиеся тесты проходят;
- typecheck проходит;
- lint и форматирование проходят;
- проверка безопасности записана;
- влияние на производительность и токены измерено или явно помечено неприменимым;
- журнал сессии существует;
- целевой коммит существует;
- итоговый отчёт простым русским языком называет оставшиеся ограничения.
